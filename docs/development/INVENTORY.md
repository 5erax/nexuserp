# Inventory application services

## Stock ledger (#49)

`InventoryModule` exports `StockLedgerService`. `post(tx, input)` takes the caller's Prisma interactive transaction: an `IdempotentCommand` runs it with the document write and audit in the same transaction. Propagate posting failures so the entire command rolls back. Passing the root Prisma client is rejected; the service never starts a separate transaction. This follows the [Prisma transaction contract](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

Only this service creates stock balances, changes `onHand` or appends movements. Balance creation uses `INSERT ... ON CONFLICT DO NOTHING`, then a conditional atomic update increments `onHand` and `version`. Movement insertion shares the transaction; a duplicate reference or duplicate opening returns `MOVEMENT_ALREADY_POSTED` (409) and rolls back the increment. Callers must keep stable document references even after the idempotency cache expires.

Inputs use exact decimal strings, at most 15 integer and 3 fractional quantity digits. `OPENING` and `ADJUSTMENT_IN` require a positive delta; `ADJUSTMENT_OUT` and `SHIPMENT_OUT` require a negative delta. Inbound `unitCost` is optional/null or nonnegative with at most 14 integer and 6 fractional digits; outbound cost stays null. Invalid inputs fail before SQL can silently round them. A positive balance overflow returns `STOCK_LIMIT_EXCEEDED` (409).

Outbound updates require the resulting `onHand >= reserved`; insufficient available stock returns `INSUFFICIENT_STOCK` (409), with exact `variantId`, `requested` and `available` strings. Reservations do not change on-hand; shipment consumption must release the matching reserved quantity and post its outbound movement within one caller transaction (#50).

The service has no public HTTP endpoint. The caller owns permission/branch checks and document lifecycle rules; composite foreign keys still reject cross-organization references. Opening/adjustment authorization and approval arrive in #51, and scoped warehouse/read APIs in #53. Archived products are not a blanket prohibition here: existing stock still needs controlled correction/depletion.

`stock-ledger.integration-spec.ts` checks exact decimals, all four movement types, insufficient available stock, concurrent first receipts and last-unit outbound races, duplicate references/openings, foreign references, immutable history, idempotent replay and full caller rollback. `stock-ownership.spec.ts` guards explicit Prisma/SQL writes outside the ledger while allowing reservation-only balance updates. Tests clean only UUID-owned fixtures in an explicit `_test` database.

## Reservations (#50)

`InventoryModule` also exports `ReservationsService`: `reserve(tx, {organizationId, warehouseId, referenceId, items})`, `release(tx, selection)` and `consume(tx, {...selection, createdBy, shipmentId})`. The same reference identifies the whole reservation batch (1–100 unique variants), not one line; references cannot be reused after release/consumption. There is no public reservation endpoint. The Sales migration adds the order-item FK and requires it on new ACTIVE reservations. Callers validate the warehouse/branch and business document, propagate errors, and commit the document/audit with Inventory changes in one transaction.

A transaction advisory lock on organization/reference serializes duplicate reserve commands and competing release/consume commands. UUID case is normalized for the lock and variant lookup. Balances are then locked in ascending immutable balance ID order, independently of input line order. Conditional updates enforce `onHand - reserved >= quantity` before incrementing reserved; a missing balance means zero available. Failure of any line aborts the entire command. The `(organizationId, referenceId)` index supports batch lookup without scanning the organization's reservation history.

Release changes ACTIVE reservations to RELEASED and subtracts reserved. Consume changes them to CONSUMED, subtracts reserved and calls the ledger for each negative SHIPMENT_OUT movement with the stable shipment ID. Both are terminal transitions; repeated or mixed terminal requests return `RESERVATION_NOT_ACTIVE` (409) without another balance change. `STOCK_BALANCE_MISMATCH` (409) stops consumption/release if the aggregate reserved quantity is corrupt; investigate/repair with approved documents rather than clamping a balance. Each balance mutation increments version; consume increments it for both reserved and on-hand changes.

Command transactions use `withTransactionRetry` through the idempotency framework: READ COMMITTED plus explicit locks/conditional updates. Only a confirmed PostgreSQL deadlock/serialization abort (Prisma P2034, or P2010 with the pinned pg adapter's TransactionWriteConflict cause) retries the entire callback, at most three attempts with 10/20ms backoff. It rechecks authorization, reclaims idempotency and repeats all database changes after rollback. Exhaustion returns TRANSACTION_CONFLICT (409); timeouts, lost connections and business failures are not automatically retried. Callbacks must contain database operations only, without irreversible network side effects. See [PostgreSQL deadlocks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-DEADLOCKS).

`reservations.integration-spec.ts` verifies all-or-nothing, exact decimals, duplicate/terminal protection, last-unit contention, reverse SKU ordering, organization isolation, shipment rollback, an actual two-connection deadlock, serialization rollback and bounded retry. The idempotency suite also verifies a retried aborted command leaves one key and one business write. `stock-concurrency.integration-spec.ts` adds 20 rounds of 100 contenders, reverse SKU commands and 100 concurrent retries, with reconciliation after each stage; see the [test strategy](../testing/TEST_STRATEGY.md#inventory-concurrency-54) for commands and mutation evidence.

## Reconciliation (#52)

`GET /api/v1/inventory/reconciliation` requires `inventory.balances.read` with ORG scope. This is the explicit organization-wide inventory administration grant; role names do not bypass it, and BRANCH grants receive 403. The organization always comes from the authenticated actor. Query parameters are `page` (default 1), `pageSize` (default 20, maximum 100) and optional `warehouseId`; a foreign/missing warehouse returns 404. Active and archived warehouses/SKUs are included because their history still matters.

Each result identifies warehouse, branch and SKU, with exact three-decimal strings `onHand`, `expectedOnHand` (sum of all movements), `reserved` and `expectedReserved` (sum of ACTIVE reservations). It also flags `missingBalance`. A full join detects ledger history missing its aggregate row and nonzero balances without ledger entries; absent aggregate sums are zero. Count and page use one REPEATABLE READ snapshot to avoid false drift/page-count differences during concurrent posting. Results are sorted by warehouse/variant UUID for stable paging. The endpoint only reports differences and never changes balances or history.

Maintenance CLI (requires a privileged database connection, bypasses HTTP/session authentication):

```sh
pnpm --filter @nexus/api inventory:reconcile <organization-uuid> [page]
```

It returns JSON for one page of at most 100 differences and a total count. Exit 0 means no differences in the organization; exit 2 means differences exist even if the requested page is empty; exit 1 means invalid arguments, missing organization or a configuration/database failure. Request further pages when total exceeds 100; each request/CLI page takes its own snapshot. `ReconciliationService.check` is the trusted maintenance/test interface; HTTP callers use the permission-checked `list` method.

When drift appears, record the organization/warehouse/SKU, actual/expected values and requestId, then pause posting for that warehouse while investigating. Check immutable movement references, document status, active reservations and transaction/error logs. Do not overwrite `onHand`/`reserved`, delete history, or treat a read report as permission to repair. Corrections require the approved document workflow (#51) and a reviewed cause-specific repair if an aggregate/reservation is corrupt. Re-run reconciliation after the controlled repair and resume writes only when the cause and result are verified.

`reconciliation.integration-spec.ts` exercises HTTP/CLI exit codes, both kinds of drift, missing balance/ledger cases, pagination, exact decimals, current grant changes and cross-organization isolation. Corruption is introduced only into UUID-owned test fixtures and restored/cleaned there; production code remains read-only.

## Warehouses and reads (#53)

`GET /warehouses` and `GET /warehouses/:id` require `inventory.warehouses.read`; ORG sees its organization, BRANCH only the actor's granted active branches. Lists support q (code/name), branchId, status and server pagination. `POST /warehouses` and `PATCH /warehouses/:id` independently require warehouses.manage ORG, rechecked inside the write transaction. POST uses the command idempotency framework; configuration changes and audit commit together.

Warehouse codes are trimmed/uppercased and unique per organization. Branch belongs to the organization and must be active for a new/active warehouse. Branch assignment cannot change after creation, so historical stock cannot silently move to another branch. Choosing an active default atomically clears the previous active default in that branch, with an audit event for both changes; an organization lock serializes competing switches. Existing stock/order references keep the old warehouse ID. Archiving clears isDefault, requires no ACTIVE reservation, and retains balances/movements for historical reads. A warehouse can be inactive with remaining unreserved stock; no stock is transferred or deleted. Archiving also refuses a CONFIRMED Sales order. The Sales-schema integration test verifies that switching the default preserves warehouse IDs already snapshotted on orders.

Create defaults to ACTIVE/non-default when those fields are omitted. PATCH fields are all optional in the generated client; omitting status/isDefault preserves their stored values, including name-only edits of inactive or default warehouses. Request schema metadata intentionally omits inherited default values so typed clients are not forced to send state changes.

`WarehousesService.lockActive(tx, organizationId, warehouseId)` is the trusted business-caller interface after document authorization. It holds FOR SHARE locks on warehouse and parent branch until commit, returning id/branchId only when both are active. Posting/confirm callers use it before Inventory writes so configuration cannot change halfway through a command; passing the root Prisma client is rejected. This interface does not replace caller permission/document scope checks.

`GET /inventory/balances` requires balances.read and returns exact onHand/reserved/available strings plus lowStockThreshold and a boolean alert. `available = onHand - reserved`; alert is inclusive (`available <= threshold`), including zero stock at the default zero threshold. Lists contain balance rows already created by the ledger, rather than every possible warehouse/SKU combination. `GET /inventory/movements` independently requires movements.read and returns immutable quantity/cost strings, creator UUID and source type/reference UUID. Optional filters are warehouseId, variantId, q (SKU/variant/product name); movements add referenceType, referenceId and inclusive from/to ISO dates. Archived entities remain readable within scope.

Warehouse and balance lists apply organization and warehouse-branch scope before counting/pagination (maximum 100), with count/rows in one REPEATABLE READ snapshot. Balances sort by updatedAt/id and warehouses by createdAt/id using the validated asc/desc order. Movements use a descending createdAt/id cursor timeline: limit defaults to 20 (maximum 100), cursor is opaque and validated, and meta.nextCursor is null at the end; there is no total, page, pageSize or sortOrder. Each request reapplies scope and filters, so new movements do not shift subsequent page boundaries. Keep filters unchanged while following a cursor. A foreign warehouse detail returns 404; a list filter outside scope returns zero records. There is no direct balance-write API. Existing warehouse/variant/time indexes and the new organization/referenceId movement index support these paths; API latency targets still require measurement in #77.

`warehouses.integration-spec.ts` covers branch/organization scope before count, exact availability/threshold boundaries, reference/date/SKU filters, idempotent create, default switching races, active reservation protection, audit rollback, current permission removal, inactive parents and real warehouse/branch lock exclusion across connections.

## Opening and adjustment commands (#51)

`POST /inventory/adjustments` creates a DRAFT with a required reason and 1–100 unique SKU lines in one active warehouse/branch. OPENING deltas must be positive; ADJUSTMENT deltas are signed and nonzero. Quantities use exact three-decimal strings; optional inbound cost has six decimals, and outbound cost must be null. Zero cost and unknown cost remain distinct. Opening stock is accepted only before any movement for that warehouse/SKU; the ledger checks history while holding the balance lock.

The server snapshots INVENTORY_APPROVAL_THRESHOLD (default 10) when creating the document. `POST /:id/post` posts DRAFT when the sum of absolute deltas is at or below that snapshot. Above it, the command returns PENDING_APPROVAL without changing stock. `POST /:id/approve` requires another actor with adjustments.approve in scope, and returns APPROVED. A subsequent post command writes every movement, balance, POSTED state and audit in one transaction. Negative adjustments cannot consume reserved stock. `POST /:id/reject` requires approval permission and a nonblank reason, records REJECTED and changes no stock. `POST /:id/cancel` requires create permission in scope and accepts DRAFT/PENDING_APPROVAL/APPROVED, including an inactive warehouse. These four commands return 200; create returns 201. POSTED/CANCELLED/REJECTED cannot transition again. No edit or delete API is exposed; corrections use a new document.

Every command requires its own UUID Idempotency-Key, retaining that key only when retrying the same uncertain action. The initial post that requests approval always replays its original PENDING_APPROVAL response, even after approval. Generate a fresh key for the subsequent posting action. Commands reauthorize the current session, grant and branch scope inside the transaction before first execution or cached replay. Organization shared locks freeze authority changes; document and ordered balance locks serialize stock/state changes. Approval/post/create require an active warehouse and branch. A failed ledger/audit operation rolls back stock, document and key together.

`GET /inventory/adjustments` and `GET /inventory/adjustments/:id` use movements.read with ORG/BRANCH scope. The paged list returns summaries/itemCount; only detail loads the bounded item list. Filters: warehouseId, kind, status and q (reason/SKU), with scope applied before count/pagination. Foreign detail is 404. The database also protects posted documents and lines from rewriting or moving them into another document; this complements the API state checks.

## Inventory workbench (#56)

The protected `/inventory` page exposes balance, movement and document views independently according to read grants. Warehouse and SKU lookups are paged, so options beyond the first 20 remain reachable. Balance rows show exact physical/reserved/available quantities with a textual low-stock warning. Movement filters include SKU text, warehouse, source type and UTC dates; cursor navigation retains filters and source links open the adjustment document. Shipment UI links arrive with Sales rather than pointing to an unavailable route.

Create OPENING/ADJUSTMENT documents by adding 1–100 unique SKU rows manually. Unknown inbound cost is blank/null; explicit 0 remains 0. Negative adjustments cannot include cost. The form checks sign/precision/duplicates and the API validates again. No CSV parser is added: manual entry is the selected bulk-input path. Draft detail shows the snapshotted threshold and exact absolute total; actions depend on current grant, branch scope and state. Self approval is hidden; backend still enforces the rule. Rejection requires a reason; posted documents expose no edit/delete controls.

An uncertain create/action freezes its payload and retains its UUID for retry. Detail retains a retry control even if a background refresh observes the new state. Successful cached replay refetches the document before the next action, avoiding stale PENDING_APPROVAL after another actor has approved; a later posting action uses a fresh UUID. Unit tests cover exact null/zero values, retry keys, invalid lines and action visibility. The existing two-actor browser scenario now checks lost create response, approval, posting, balance/movement reads, negative adjustment, 390px layout and accessibility without adding logins or changing rate limits.

## Reservation references after the Sales migration (#58)

ReserveInput.items now requires a real orderItemId. referenceId identifies its Sales order. Inventory locks the order shared before the reference/balance locks, validates the same organization/order/warehouse/variant and exact line quantity, then writes the FK together with the reservation. New ACTIVE rows cannot omit the link. RELEASED/CONSUMED Phase 2 history may retain null. Sales callers still lock their order for update first and own the complete transaction; no public endpoint creates an unlinked reservation. Batch test fixtures create real Customer/Order/Item rows before contention, retaining the original 100-request/20-round stock assertions. Customer eligibility and full Sales lifecycle validation belongs to the Sales/Finance commands, not this Inventory interface.
